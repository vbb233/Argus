# Argus 改造记录

> 基于开源项目 [DevYangJC/Argus](https://github.com/DevYangJC/Argus) 的二次开发
> Fork：`vbb233/Argus`　分支：`master`
> 技术栈：Java 21 / Spring Boot 3.5 / Spring AI 1.1.2 / PostgreSQL+pgvector / Elasticsearch 8 / MinIO / Vue 3.5

本文记录在原有 RAG 知识库平台基础上**发现并修复的 5 个缺陷**，以及为保证结论可信而
建立的评测方法。每个缺陷都按「现象 → 证据 → 根因 → 修复 → 度量」推进。

## 二、缺陷 1：提示词花括号未转义，查询规划完全失效

Spring AI 的 `StTemplateRenderer` 以 `{` / `}` 作为 ST4 模板定界符。
查询规划提示词里有一个 JSON 输出样例：

```
返回格式：{"strategy": "DIRECT", "reason": "..."}
```

`{` 被当成模板表达式起始符 → 渲染直接抛异常。
**用户视角**：所有问题的查询规划都走不到，策略退化为默认值，
`REWRITE` / `DECOMPOSE` / `GLOBAL` 三条路径全部不可用。

**修复**：字面量花括号转义为 `\{` `\}`。
**教训**：这是"静默降级"——接口不报错、答案还能出，只是质量悄悄变差。
只有看日志才发现 `strategy` 永远是同一个值。

## 三、缺陷 2：模型名与费率硬编码

`QaService` / `AssistantService` 里写死了 `MODEL_NAME = "qwen-plus"`，
而实际部署用的是 DeepSeek。后果是 `llm_usage_records` 按错的模型名与费率计费。

**修复**：新增 `LlmProperties`（`@ConfigurationProperties("argus.rag.llm")`），
模型名与费率表改为配置项，未知模型打 WARN 而非静默按 0 计费。

## 四、缺陷 3：GLOBAL 策略只注入 1/32 的内容

### 现象

问题「第5学期一共开设了多少门课程？」被查询规划**正确判定为 `GLOBAL`**，
但答出「**8 门**」，且列出的 8 门里有 3 门**根本不属于第 5 学期** —— 是编造。

### 根因

```java
// 注释本身就说明了意图
/** 执行全局遍历检索，提取群组内所有 READY 状态文档的首个切片。 */
DocumentChunkEntity primaryChunk = activeChunks.stream()
        .filter(c -> c.getChunkIndex() != null && c.getChunkIndex() == 0)
        .findFirst()      // ← 每个文档只要 chunk 0
        .orElse(activeChunks.get(0));
```

该 PDF 共 32 个切片，课程表在第 8~9 页（chunk 20+）。
只给 chunk 0（"专业简介"）= **有效覆盖率 3%**。

### 修复

遍历全部切片（按 `chunkIndex` 排序），并加两级字符预算防止上下文与成本失控：
单文档 24000 字符、合计 120000 字符，触顶打 WARN。

### 度量

| | 修复前 | 修复后 | 独立解析真值 |
|---|---|---|---|
| 第5学期课程数 | 「8 门」+ 3 门编造课程 | **「16 门」** | 16 门 |

日志可证：`全局遍历检索: 文档数=1, 切片数=32, 累计字符=9650, 被截断文档数=0`。

> **诚实记录**：我曾据此报告"事实类准确率提升 1.4pp"，但 3 次重复评测证明
> 那 1.4pp 是采样噪声。**该修复对事实类问题没有可测影响**，
> 它的真实价值只体现在上面这类聚合问题上。

## 五、缺陷 4：PDF 竖排表头被逐字打散（核心工作）

### 现象

144 条评测集里 `semester`（第几学期开课）类准确率长期低于 `credit`（几个学分）类
（91.3% vs 95.7%），且有 5 条**稳定失败**。

### 第一步：先看后端到底说了什么

复现请求，拿到原始响应：

```json
{
  "answered": false,
  "reasonCode": "EVIDENCE_NOT_COVERED",
  "reasonMessage": "证据未明确给出「程序设计基础」课程本身的授课学期；
                    仅显示「程序设计基础课程设计」在第2学期开课，二者不是同一课程。"
}
```

**这改变了问题的性质**：不是模型犯错，而是后端**结构化拒答**，且理由完全正确
—— 它识别出了同名课程陷阱并拒绝混淆。**这是设计生效，不是缺陷。**

同时暴露出评测脚本的问题：它只保留了 `answered` 和 `answer`，
把 `reasonCode` / `reasonMessage` 这两个唯一能解释"为什么拒答"的字段丢掉了。

### 第二步：证据里到底缺了什么

从数据库取回命中的分块：

```
1960209 HarmonyOS应用开发 6 3 2 48 24 24
1960283 数字逻辑 4 2 2 32 24 8
1960813 团队激励与沟通 5 2 1 24 12 12     ← 目标课程
1960873 Linux系统 5 2 1.5 32 20 12
```

**数据行完整，但整块没有任何表头。** 再往前翻，表头在另一个分块的末尾，长这样：

```
课
程
类
别
授
课
学
期      ← 就是它，一个字一行
周
学
时
```

### 第三步：根因（坐标证据）

中文表格的表头单元格常**竖排**排版。这种版面下：

- 同一单元格内的字符 **x 坐标完全相同**，y 坐标递增
- 不同单元格共享 y 区间，x 坐标递增

而 `PDFTextStripper` 按 **(y, x)** 线性输出 → 把同一高度上来自不同单元格的字符**交错**输出。

坐标探针（`tools/HeaderProbe2.java`，第 8 页 y∈[78,150]）实测：

```
x=  55.860  y=  95.019  '课'      ← 同一列的 4 个字，x 完全相等
x=  55.860  y= 106.539  '程'
x=  55.860  y= 118.058  '类'
x=  55.860  y= 129.578  '别'
x=  84.660  y=  94.969  '修'      ← 下一列
```

### 第四步：修复

新增 `LayoutAwarePdfTextStripper`，采用**最小侵入**策略：

1. **完全沿用** `PDFTextStripper` 的行切分与词文本 —— 正常文本逐字不变
2. 识别**连续的单字符行**（≥4 行）作为竖排片段
3. **只对竖排片段**改用坐标重建：按 (x, y) 重排（即把「先行后列」纠正为「先列后行」），
   按 x 聚类成列，列间插入分隔符

边界处理：若某片段每列只有 1 个字符，说明它其实是**横向文字**被换行拆散
（如分组标题 `通识教育课必修，共５８学分，１０６学时`），此时改为无分隔拼接，
避免产生 `通 | 识 | 教 | 育` 这种噪声。

**一个反面教训**：我第一版加了 `setSortByPosition(true)` 想让行切分更稳定，
结果**反而把修复搞坏** —— 开启后 PDFBox 不再把表头拆成单字符行，而是合并成
`课修课授授实上程其` 这种交错行，**「单字符行」这个特征本身消失了**。

### 第五步：度量

| | 修复前 | 修复后 |
|---|---|---|
| 解析字符数 | 9282 | 8572 |
| 表头 | 20+ 个单字符行 | `课程类别 \| 修读类别 \| ... \| 授课学期 \| 周学时 \| 学分 \| ...` |
| **与修复前逐字相同的行** | — | **346 / 354 = 97.7%** |

同一次改动还加了**表头传播**：含 ≥2 条数据行的分块向前回溯最近表头并注入。
重新入库后 32 个分块中有 13 个获得表头。

原失败条目的定向验证：

| 问题 | 修复前 | 修复后 |
|---|---|---|
| 程序设计基础在第几学期 | 0/3 拒答 | ✅ 第1学期 |
| 数据结构在第几学期 | 0/3 拒答 | ✅ 第4学期 |
| 操作系统在第几学期 | 不稳定 | ✅ 第5学期 |
| 团队激励与沟通在第几学期 | 不稳定 | ✅ 第5学期 |
| 软件质量保证与测试是几个学分 | 不稳定 | ✅ 1.5学分 |

### 第六步：全量 A/B（136 条 × 3 次 × 2 组语料 = 816 次调用）

同一份 PDF 分别用旧解析器与新解析器入库，两组语料各跑 3 次取多数票：

| 类型 | n | 旧解析器 | 新解析器 | 变化 |
|---|---|---|---|---|
| credit（几个学分） | 69 | 65 = 94.2% | **67 = 97.1%** | **+2.9pp** |
| semester（第几学期） | 61 | 57 = 93.4% | **60 = 98.4%** | **+5.0pp** |
| aggregate（聚合） | 3 | 3 = 100% | 3 = 100% | ±0 |
| negative（应拒答） | 3 | 3 = 100% | 3 = 100% | ±0 |
| **事实类合计** | **133** | **125 = 94.0%** | **130 = 97.7%** | **+3.7pp** |
| 陷阱命中率 | 133 | 0.0% | 0.0% | ±0 |

- **`semester` 类 +5.0pp —— 正是本次修复针对的那一列。**
- 136 条中 **131 条判定完全未变，变化的全是改善，零回退。**
- 这与解析层"97.7% 的行逐字相同"互为印证：改动精准命中目标，没有误伤正文。

> **诚实记录**：首次用 144 条口径测出的是 +0.7pp，还伴随 6 条"回退"。
> 追查后发现是评测集与评分器各有缺陷（见第七节），修正后才得到上面的干净结果。

## 六、缺陷 5：数据行分块缺少表格标题

课程 `<软件工程>` 的数据行只出现在**一个**分块（chunk 21）里，
而「软件工程」作为**专业名**出现在**十余个**分块中。

**后果**：问题「软件工程在第几学期开课」的检索被专业名主导，
命中「专业主干课程：软件工程（48学时）」那一节，而不是课程表行 → 稳定拒答。

**修复**：`withTableHeader` 扩展为 `withTableContext`，除表头外再回填表名，
前缀分别为 `[所属表格]` 与 `[表格表头]`，让分块带有表格级语义锚点。

修复后的分块（documentId=4, chunk 21）：

```
[所属表格] 软件工程专业课程设置表
[表格表头] 课程类别 | 修读类别 | 课程号 | 课程名称 | 授课学期 | 周学时 | 学分 | ...
1960073 软件工程 3 3 3 48 48
1460076 软件项目管理 6 2 2 32 32
```

### 实测效果（各问 3 次）

| 问题 | 修复前 | 修复后 |
|---|---|---|
| 软件项目管理是几个学分？ | 0/3 错（答 165 或拒答） | **✅ 3/3「2学分」** |
| 软件项目管理在第几学期开课？ | 0/3 拒答 | **✅ 3/3「第6学期」** |
| 软件工程是几个学分？ | 0/3 错 | ❌ 仍答「专业总学分 165」 |
| 软件工程在第几学期开课？ | 0/3 拒答 | ❌ 仍拒答 |

**2/4 修复。** `软件工程` 两条仍失败，原因已定位但未解决：
「软件工程」作为专业名出现在**十余个**分块中，其中
「专业主干课程：软件工程（48学时）」一节与问题高度相关，
检索仍优先命中它而不是课程表行 `1960073 软件工程 3 3 3 48 48`。
这属于**同名实体消歧**，不是表格结构问题 ——
需要实体级加权（例如在重排阶段提升"包含与查询实体匹配的表格行"的分块），
尚未实现。

## 六之二、缺陷 6：计数类问题没有拿到全量证据

### 现象

聚合类评测集中，「第N学期必修课程的学分」8 条全部 3/3 正确，
而「第N学期一共开设了多少门课程」全部失败（模型答「5 项」，实际 8 项）。

### 根因

复现一次，看证据覆盖情况：

```
coverageMode  : RELEVANCE_ONLY     ← 不是 GLOBAL
evidenceCount : 4
命中的分块     : chunk 20 / 17 / 29 / 26
```

**只能看到表的一小部分。** 第 5 学期的 16 门课散布在多个分块里，
只给 4 个分块，模型数出来的必然偏小。

`GLOBAL` 策略本来就是为这类问题设计的（遍历全部切片），
提示词也要求模型在这类问题上选择 `GLOBAL` —— **但实测选择不稳定**。

### 修复

在 `QueryPlanningService` 中加一条**确定性兜底**：命中计数/枚举特征即强制 `GLOBAL`，
不再依赖大模型判断。

```
多少门 | 几门 | 哪几门 | 哪些课 | 一共 | 总共 | 共计 |
所有的?课程 | 全部课程 | 各学期 | 每个学期 | 每学期
```

规则必须精准 —— 误命中会把普通单点问题也变成全量遍历，抬高成本与延迟。
因此测试里同时覆盖 6 个正例和 5 个反例（如「软件工程专业毕业要求的总学分是多少」
不应命中）。

### 实测效果

| 问题 | 修复前 | 修复后 |
|---|---|---|
| 第5学期一共开设了多少门课程？ | 0/3（答「1x 项」，偏小） | **✅ 3/3「16门」** |

第 5 学期是我唯一独立验证过真值的学期（16 门，见第五节 v4 解析器），
它修好了，说明机制有效。

### 但同时发现：这一族问题本身歧义

其余学期仍不过，但我没有把它记成模型缺陷 —— **因为我的真值不可信**
（同一批数据我的解析器已经错过 5 次）。核实后发现真正的问题是：

- `3300020 军训 1 2` 只有 2 个数值列，我的解析器跳过了它，模型把它算作一门课
- 于是两边都能得到「8 门」，但**组成不同**

**「多少门课程」是否包含集中性实践环节（军训、课程设计）没有定义。**
所以这 6 条已从聚合评测集中移除 —— 先对齐口径，而不是改模型。

### 清理后的聚合类评测结果

剔除歧义条目、并把「学科基础课要求的最低学分」改为「学科基础课合计多少学分」
（原文比例表给的是"合计"，用"最低"会让模型去找门槛值）后：

| 类别 | 条数 | 结果 |
|---|---|---|
| 各学期必修课程学分（原文分布表） | 8 | **8/8，全部 3/3** |
| 文档自述总量（总学分/总学时/通识/集中实践/学科基础/数学类） | 6 | **6/6，全部 3/3** |
| **合计** | **14** | **100%，判定一致率 100%，噪声 0%** |

## 七、评测方法：我的测量工具本身错了三次

这部分和代码修复同等重要 —— **测量工具的故障会伪装成被测对象的缺陷。**

### 7.1 丢弃诊断字段

评测脚本早期只存 `answered` / `answer`，丢掉 `reasonCode` / `reasonMessage`。
后果：5 条失败被笼统归结为"模型能力不足"，而其中 1 条其实是
**后端正确识别同名陷阱后拒答**。修法完全不同。

### 7.2 JWT 过期被记成"模型拒答"

首次用 `--repeat 3` 重跑，结果**断崖式跌到 46.1%**，失败模式极其规整：
前 65 条全对，第 66 条起连续 79 条全部"拒答"。

根因是脚本只在开头登录一次，而 token 30 分钟过期、432 次调用要跑 40 分钟 ——
**30 分钟后所有请求返回 401，被记成了拒答**。

识别特征：失败"从某一刻起"整齐开始、跨越所有类型与难度。
修复：收到 401 时惰性重新登录并重试。

### 7.3 `has_value` 假阳性

原判定是"回答里出现过目标数字就算对"。而评测集里有 8 条
**提问文本完全相同、期望值各为 1~8** 的条目（`形势与政策在第几学期开课？`）。
旧回答较长、把 8 个学期都列了出来，于是**任何期望值都能匹配** —— 8 条全部假阳性通过。

修复：改为**槽位匹配** —— 数值必须出现在问题所指的槽位里
（credit → `N 学分`；semester → `第N学期`）。这样
`第1至第8学期` 只解析出 `{1, 8}`，期望 5 就不会误判为命中。
同时支持中文数字（模型可能答"第五学期"）。

### 7.4 负样本判定过严

原逻辑只认 `answered=false` 为正确拒答。但后端还有第二种拒答风格：
`answered=true` + 正文说明"证据未给出…无法确认"。
后者被判成作答 —— 真实拒答质量被低估。修复：加入委婉拒答识别。

### 7.5 真值本身错了五次

| 版本 | 错误 | 后果 |
|---|---|---|
| v1 | 正则漏掉带组标记的行 `组21960059 ...` | 真值 12 门，**误判模型答「16 门」为错** |
| v2 | `组[0-9]+` 贪婪匹配，把课程号一起吃掉 | 真值 13 门，仍错 |
| v3 | 漏掉跨行折行的行 | 真值 15 门，仍少 1 |
| v4 | 增加跨行回溯 | 真值 16 门，与模型一致 |
| v5 | **重新实现时又踩了 v2 的坑** | 第5学期少算 4 门 |

**这个过程本身就是证据**：连专门写解析器读这一层文本都要反复五次才对，
说明 PDF 文本层确实不适合承载结构化信息。区别在于人有条件反复验证，
而 LLM 在一次问答里做不到。

## 八、一个被误判为"模型缺陷"的案例

我曾把「第5学期总学分」答 9.75（我以为真值 32.50）列为
"长上下文聚合可靠性不足"的证据，并准备据此改提示词。

**后来发现模型是对的。** 培养方案里有张表，标题就叫
**「软件工程专业各学期必修课程学分分布情况表」**：

```
第1学期 第2学期 第3学期 第4学期 第5学期 第6学期 第7学期 第8学期
20.25  24.25  24.75  16.25  9.75   11.25  13.25  12.25
```

- 第 5 学期**必修**学分原文就是 9.75，模型答的正是这个。
- 我的 32.50 是把该学期**所有**课程行相加，其中含 `组1`~`组5` 选修备选组
  （一个学生不会全选）。
- 内部一致性：`20.25+24.25+24.75+16.25+9.75+11.25+13.25+12.25 = 132`，
  再加集中实践 `33` = **165** = 毕业要求总学分 ✓

**所以问题在于我的提问有歧义，而不在模型。**
我据此重建了聚合类评测集（20 条），提问改为「第N学期**必修课程**的学分是多少？」，
真值直接取自原文表格而非自行求和。

## 九、沉淀下来的方法论

1. **先看后端说了什么，再判断是谁的错。** 「拒答」至少有两种截然不同的成因：
   检索到了但缺关键列（该修数据通路），或检索到的是同名不同实体（该修消歧）。
   表现相同，修法完全不同。

2. **不要丢弃诊断字段。** 丢掉 `reasonCode` / `reasonMessage` 等于自废双眼。

3. **LLM 任务必须重复采样。** 单次运行 ±1~2pp 的差异是噪声，不能作为结论。
   本次采用每条重复 3 次取多数票，并报告稳定性（判定一致率）。

4. **区分"系统性失败"与"采样噪声"。** 3 次全失败的才是真缺陷；
   判定在多次间摆动的不应误判为 bug。

5. **改动要可度量。** 97.7% 的行逐字相同，是"没有误伤"的直接证据。

6. **质疑自己多过质疑模型。** 本次真缺陷、3 个测量工具缺陷、
   5 次真值错误 —— 后两类加起来比前一类还多。

## 十、缺陷 7：表格行召回不足 → 行级分块 + 查询蒸馏

### 现象

`软件工程` 两条问题稳定失败。诊断发现**含目标行的分块从来没被检索到**：

| 问题 | 实际命中的分块 | 目标行所在分块 |
|---|---|---|
| 数据结构在第几学期（答对） | 20, 24, 11 | 20/24 里有 ✅ |
| 软件工程在第几学期（答错） | 18, 8, 29 | 21 里有，**但没被检索到** ❌ |

所以问题不在重排 —— **目标分块根本没进候选集**。

### 根因一：单行数据在分块里词密度太低

一张课程表被切成几百字的混合分块，一个分块里可能有 10 行课程，
目标行只占 1/10。检索时很容易被大段叙述文字挤掉。

**修复**：为每条表格数据行**额外**生成行级分块，内容为「表名 + 表头 + 该行」，
策略标识 `table-row-v1`。追加而非替换，原分块索引与内容不变。

效果：目标分块在关键词通道从第 13 位升到第 10 位 —— **仍然不够**。

### 根因二：提问用语与文档列名词汇不匹配（真正的根因）

用户问「在第几**学期开课**」，而表格的列名是「**授课学期**」。
「开课」这个词在文档里根本不存在，检索只能靠「软件工程」这类高词频词排序，
于是大段叙述文字胜出。

实测对比（目标分块排名）：

```
"软件工程在第几学期开课"           -> 第 10 位（进不了 top-5）
"软件工程在第几学期开课 授课学期"  -> 第  7 位  ← 只往后加词，几乎无效
"软件工程 授课学期"               -> 第  2 位  ← 蒸馏后才有效
```

**为什么「加词」无效而「蒸馏」有效**：长查询里的「在 / 第 / 几 / 学期 / 开课」
这些通用词在大段叙述文中反复出现，把目标分块压了下去；只有把查询压缩成
「实体 + 列名」，词密度才回到目标分块这一侧。

**修复**：新增 `distilledTableQuery`，把「实体 + 口语化属性问法」蒸馏为
「实体 + 文档列名」（如 `软件工程 授课学期`），作为**额外一路**查询参与融合，
原查询保留。抽不出具体实体（含指示代词、过长）时返回 `null`，保持原行为。

### 一个必须处理的副作用

行级分块让文档内容从约 8.5K 字膨胀到约 27K 字，而 `GLOBAL` 遍历的单文档预算是
24000 字符 —— **会触发截断，把表格尾部切掉**。
由于行级分块是常规分块中表格行的同内容副本，`retrieveGlobal` 现在跳过它们。

### 效果

| 指标 | 仅竖排表头修复 | 再加行级分块 + 蒸馏 |
|---|---|---|
| credit | 97.1% | **98.6%** |
| semester | 98.4% | 98.4% |
| 事实类合计 | 97.7% | **98.5%** |
| 判定一致率 | 96.3% | **99.3%** |

改善 1 条（#87 软件项目管理学分），**零回退**。
聚合类评测集同时保持 14/14 = 100%。

`软件工程在第几学期` 从 0/3 变成 1/3（首次答对「第3学期」），但**仍不稳定**；
`软件工程是几个学分` 仍 0/3。这两条是全部 133 条事实类问题里仅剩的失败。

## 十二、缺陷 8：同名实体无法可靠命中 → 实体级检索通道

### 为什么前面所有手段都不够

行级分块让目标行单独成块，查询蒸馏把排名从第 10 位提到第 2 位，
但**融合后是否进入 top-5 仍然取决于运行时的召回抖动**：

```
实测 chunk75（含「1960073 软件工程 3 3 3 48 48」）的出现率：约 40%
出现时 → 答对「第3学期」；未出现时 → 拒答
```

根因是**排序本质上是相关性问题，而这里需要的是确定性问题**：
「软件工程」既是课程名、又是专业名，向量与关键词两路都会被大段专业介绍淹没。
只要有排序，就存在把它挤出 top-k 的可能。

### 方案：绕开排序，按名称精确查

1. **入库时写入结构化字段**：行级分块把表格行的编号与名称写入
   `metadata_json.rowCode` / `rowName`。
   → 必须精确匹配单个字段。若改为对整行文本做 LIKE，
   「软件工程」会命中**全部**行级分块（表名「软件工程专业课程设置表」里也含这个词），
   等于没有筛选。
2. **检索时按名称精确取回并置顶**：`selectRowChunksByRowName` 一次命中唯一正确分块，
   直接插到证据最前面，完全绕开向量/关键词/融合链路。
3. **抽出实体**：复用 `TableEntityExtractor`（与查询蒸馏共用同一套规则，
   避免两处各写一份而逐渐漂移）。抽不出具体实体就什么都不做。

### 一个静默失效的坑

第一版实现里我用 `row.get("chunkId")` 读 MyBatis 返回的 Map，
**拿到的是 null** —— 因为 PostgreSQL 会把未加引号的列别名折成小写（`chunkid`）。
项目里本来有 `getValue(row, field)` 做驼峰/小写兼容查找，我没用。

症状极隐蔽：**不报错、不抛异常，通道就是一条证据也加不进来**，
只能靠比对 `evidenceCount` 从 4 变 5 才发现。
改成 `getValue` 后立刻生效。

### 效果

| 问题 | 实体通道前 | 实体通道后 |
|---|---|---|
| 软件工程在第几学期开课？ | 1/3（不稳定） | **4/4 全对「第3学期」** |
| 软件工程是几个学分？ | 0/3 | **4/4 全对「3学分」** |
| 目标分块出现率 | 约 40% | **100%** |
